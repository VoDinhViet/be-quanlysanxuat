# Workflow Rules

- Package manager is **pnpm**. Never use `npm` or `yarn` commands in this repo.
- Don't run `pnpm build`/`pnpm lint`/`pnpm format` after every small edit (a rename, a one-line tweak) — it's slow and the user finds it disruptive. Only run them once at the end of a larger unit of work, before declaring a non-trivial task done, or when the user explicitly asks.
- **Testing is paused repo-wide (from 2026-07-28)**: don't create new `*.spec.ts` files, don't update existing specs when a service/controller changes, and don't run `pnpm test`/`test:cov`/`test:e2e` as a step of the normal workflow — only do any of this when the user explicitly asks. The 50 existing spec files stay in the repo, frozen as-is; a spec drifting out of sync with unrelated code changes is expected during this pause, not a bug to fix. Use `npx tsc --noEmit` + `pnpm lint` as the safety net after coding instead (see memory "Run typecheck after coding"). To resume testing: re-add `@.claude/rules/testing.md` to `CLAUDE.md`'s import list and remove the paused banner at the top of that file.
- **Never run `pnpm db:migrate` against a shared/prod database** without explicit user approval.
- Drizzle schema changes follow edit → re-export in `schemas/index.ts` → `pnpm db:generate` → `pnpm db:migrate`, in that order (full detail in `.claude/rules/database.md`).
- Modules that were deliberately removed: `uploads` (superseded by `files`). Don't search for it or recreate it unless explicitly asked. `suppliers`/`supplier-groups` were removed and then rolled back on 2026-07-20 — they **do** exist. So do `clients`, `products`, `roles` and the RBAC schema — see `CLAUDE.md` for the current module list. `orders` also exists (added 2026-07-24) — a very early, differently-shaped `orders` module was removed at the start of the project, but the current one is a fresh, unrelated build; don't treat that old removal as a reason to avoid or recreate it.
- Talk to the user in Vietnamese. Write code (identifiers) and commit messages in English. **Write code comments in Vietnamese** (changed 2026-07-29 — was English-only before; see `.claude/rules/code-docs.md` for the doc-comment style this applies to). Follow Conventional Commits for commit messages (`feat:`, `fix:`, `refactor:`, ...).
- Before implementing a new feature (or a non-trivial change to business rules of an existing one), write or update a short spec at `docs/features/<feature>.md`. No fixed template — capture whatever the feature actually needs (typically: business rules, the API contract, error cases, and a dated "Frontend integration notes" section for any consumer-facing breaking change), not implementation details, which the other rule files already cover. Skip this for pure bug fixes or refactors that don't change behavior. Use the `doc-refactor`/`doc-generator` skills (`.claude/skills/`) to check an existing spec against its own module's code, not against a shared template.
